## §0 【先定前提】这一项与其他各项的性质完全不同

**结论先行：本游戏不是三消（match-3），而是「2×2 拼图 + 整片拖动」。《萌宠拼拼乐》里没有「横消条/竖消条/包装糖/炸弹/彩虹糖」，也没有冰块/果冻/巧克力/传送带。**

核对范围里的「3/4/5 连、L 型、T 型」「特殊糖果」「障碍格子」这三项，在 Web 原版里**一条都不存在**——不是 Cocos 漏了，是本来就没有。真正的核心玩法是：

| 规则 | 实现位置 | 口径 |
|---|---|---|
| 每图拆 4 块碎片（左上/右上/左下/右下） | `核心/pieces.ts` | `图ID = 碎片ID÷4`，`位置 = 碎片ID%4` |
| **消除 = 某 2×2 区域里 4 块同图且位置正确** | `核心/matcher.ts` `findAllPositionCorrectMatches()` | 不是连线，是拼合为完整一张图 |
| **操作 = 按住一块，把它所在的「融合组」整片刚性平移** | `核心/move.ts` `planGroupMove()` | 不是两格交换；单块时退化为两格交换 |
| 移动规则 `any`（任意距离）/ `adjacent`（每步 1 格=噩梦） | `核心/config.ts` `swapRule` | 噩梦模式 |
| **池子模型**：恒有池子5(4块)/池子1(3块)/池子2(各2块)/池子3(1块)/池子4(0块) | `核心/structure.ts` + `pools.ts` | 保证「场上恒有恰好 1 张图已集齐 4 块」 |
| 得分：每消除 1 组 **+1 分**，无连击倍率 | `核心/engine.ts:453` | §7.1 |

### ⚠️ 最关键的一条事实：Web 与 Cocos **共用同一份算法层源码**

```63:63:web/main.ts
} from '../assets/scripts/核心/index.ts';
```

```44:44:assets/scripts/玩法/GameBootstrap.ts
} from '../核心/index';
```

即：Web 原版 `main.ts` **直接 import Cocos 侧的 `assets/scripts/核心/`**。两者不是「两套实现要对齐」，
而是**同一个模块的两个消费者**。因此下列全部是**天然一致、不可能有差距**的：

`rng / pieces / grid / move / matcher / pools / collapse / merge / structure / init / refill /
forceConstruct / ledger / poolGen / config / engine / progress / honor / save`（`核心/index.ts` 全部 19 个出口）

**所以「棋盘尺寸/匹配判定/交换合法性/下落补充/池子模型/星线/续命秒数/关卡表」这些"配置与算法"，
判定一律为 `完整`，且不需要逐行比对。** 真正可能有差距的只剩**算法层的消费者**怎么用这些 API：
`GameBootstrap.ts`（Cocos 局内逻辑）vs `main.ts`（Web 局内逻辑）。

> 换句话说：本节把「有没有散落 XX 特殊糖」这类问题一次性否掉了；下面各节只查
> **「core 有的能力，GameBootstrap 有没有接」** 和 **「main.ts 里写在 core 之外的玩法逻辑，Cocos 有没有实现」**。

## 1. 棋盘与消除规则

**Web 版**（全部来自 `assets/scripts/核心/`，由 `web/main.ts:63` 直接引用该目录）：

- **棋盘形状**：严格矩形 `rows × cols`，`index = row*cols + col`（`核心/grid.ts:12-29`）。
  **没有不规则形状、没有空洞 / 不可用格**，盘面恒满格（只有「消除后→补位前」的中间态允许 `null`）。
- **尺寸：由关卡表给定**（`核心/config.ts` 的 `GRID_BY_LEVEL`）：
  1~15 关 **4 行 3 列**（12 格 / 6 图）、16~35 关 **4×4**（16 格 / 8 图）、36~60 关 **5 行 4 列**（20 格 / 10 图）；
  上限「每行 ≤4、每列 ≤5」，61~180 关沿用 5×4。
- **匹配判定：唯一消除条件**（`核心/matcher.ts:100-109` `findAllPositionCorrectMatches`）：
  某个 **2×2 区域**内 4 块碎片 **同属一张图**，且位置分别落在 **左上 / 右上 / 左下 / 右下**（拼出一张完整图）。
  **没有 3 连 / 4 连 / 5 连，没有 L 型 / T 型判定。**
- **内容完整性**（`matcher.ts:39-69`）：另一套独立的「4 块齐全」统计（**与是否相邻无关**），
  由池子模型保证场上恒为恰好 1 组 —— 这是「随时都能得分」的数学保证，不是消除条件，两者不可混用。
- **移动合法性**（`核心/move.ts:113-157` `planGroupMove`）：锚点 = 按住的那一块；
  参与的是它所在的**融合组**（`merge.ts` 的连通分量）；组内**刚性平移**；
  四种拒绝 `empty / same / rule / bounds`；`'adjacent'`（噩梦）= 曼哈顿距离恰好 1，`'any'` = 任意距离。
- **下落与补充**（`核心/engine.ts:434-479` `resolveBoard`）：消除 → `collapseColumns`（整列下压）
  → `refillGrid`（按池子模型补位，含 §4.8.4 位置交换兜底与 §4.13.2 强制构造）。
  补位一定重建成「池子5 恰好 1 张、位置拼合恰好 0 组」的合法态。
- **连锁 / 连击计分：没有。** `engine.ts:453` 固定 `this._score += 1`（§7.1：每消除一组 1 分）。

**Cocos 端**（`GameBootstrap.ts:38-44` 引用同一个 `../核心/index`）：

- 上述每项都是**同一个模块**，不存在第二份实现。
- 消费者侧：`beginLevel():276` → `new PuzzleEngine(cfg, rng)`；`doMove():491` → `engine.move()`；
  `paintAll():379` / `playResolution():523` / `playCollapse():555` 消费 `outcome.stages` 三帧快照。

**判定**：`完整`
**差距**：无（棋盘、匹配、移动、下压补位、计分全部同源）
**补齐要动**：无

## 2. 特殊糖果

**Web 版**：**没有任何特殊糖果**。全仓库不存在「横消条 / 竖消条 / 包装糖 / 炸弹 / 彩虹糖 / 条纹糖 /
色彩炸弹」这类实体的任何定义或引用，也不存在「生成条件 + 组合效果」这套机制。
不是漏做，而是**玩法本身不需要**：本作合并的是**同一张图的 4 块碎片**（拼图语义），
不是「同色连线」（三消语义）。三消里的特殊糖解决「一次消除收益太低」，本作的对应手段是
**融合组（`核心/merge.ts`）—— 已拼对的部分连成一片，可被整片搬走**，这是本作的"组合"层。

**Cocos 端**：同样没有。

**判定**：`完整`（两端皆无 → 无差距；**不是** Cocos 漏移植）
**差距**：无
**补齐要动**：无 —— 建议把这一项从待办划掉，别去找不存在的东西

## 3. 障碍与格子类型

**Web 版**：**没有任何障碍层**。不存在冰块 / 果冻 / 巧克力 / 石头 / 笼子 / 传送带 / 传送门 /
掉落出口 / 生成格 / 不可用格。难度完全由四个旋钮承担，都在 `核心/config.ts`：
① 网格（`GRID_BY_LEVEL`：12/16/20 格）；② 图池构成（每关几张图、分给几只动物、情绪分布，`poolGen.ts`）；
③ 星线（`LEVEL_STAR_LINES`，逐关给定）；④ 移动规则（`swapRule`）与时限（180/240/300 秒）。

**Cocos 端**：同样没有（共用同一份 `核心/`）。

**判定**：`完整`（两端皆无）
**差距**：无
**补齐要动**：无

## 4. 移动 / 拖动手感（唯一有实质差距的一节）

**Web 版**（`web/main.ts:2692-2835` 六件套 + `2871-2912`）：

- `dragStep` 2692：`cellSize + GAP`
- `dragLimits` 2702：四方向各能挪几格，由**最贴边的那一块**决定，**取整前**就钳住
- `dragAxes` 2736：屏幕 px ÷ `stageScale()` → 画布 px；噩梦模式**收敛到主导轴**（否则 (1,1) 会被规则拒）
- `dragFollow` 2759：拖动过程用**连续值**跟手（不取整），噩梦钳 ±1 格，再按盘边钳（可沿边滑动）
- `dragIntent` 2787：松手时 `intent`=想挪几格（取整）、`shift`=`clampShift` 后能挪几格；两者不等才有回弹依据
- `paintDrag`/`clearDragPreview` 2811/2827：跟手写 CSS 变量，**必须连变量一起删**（残留会让碎片"从别处飞来"）
- TAP_SLOP 2879：14 **屏幕** px（不随缩放变）
- 拒绝反馈 2623-2624：`'rule'` → `toast(ruleHint())`；`'bounds'` → `toast('整片挪不出棋盘')`
- 提示联动 2626-2631：连续 2 次「挪了没消除」→ `showGuide('hint4')` + `showHint()`

**Cocos 端**（`GameBootstrap.ts:394-511` + `BoardView.ts:493-509`）：

- `hitCell():401` 格缝不判空 ✓ 同口径（不留拖不动的死角）
- `axes():419` 噩梦收敛主导轴 + `min(1,·)` ✓（把 Web 的 dragAxes+dragIntent 两步合成一步，等价）
- `onTouchMove():444` 连续值 + `clampShift` 跟手 ✓（= Web `dragFollow`）
- `onTouchEnd():462-477` `intent` 与 `shift` 分离，`intent≠0 && shift=0` 给回弹 + 棋盘抖动 ✓
- `BoardView.setDragOffset():493` / `clearDrag():503` ✓
- 动画时长逐项对齐：`BoardView` 的 `ANIM` = swap .09 / recognize .06 / fit .05 / confirm .04 / vanish .35 /
  fall .26 / spawn .26 / stagger .012 / reject .3 / float .5，与 `main.ts` 的 SWAP_MS 90 / RECOGNIZE 60 /
  FIT 50 / CONFIRM 40 / VANISH 350 / FALL 260 / SPAWN 260 / STAGGER 12 / REJECT 300 / FLOAT 500 **完全相同**；
  消除 5 阶段（①识别 ②拼合 ③确认 ④消除）+ 飘字 + 落地压扁 + 补位淡入**全部存在**
  （`BoardView.setMergePhase():366` / `floatScore():383` / `playVanish():404` / `playFall():436` / `playDropIn():418`）

**判定**：`部分`

**差距**：

1. **规则拒绝没有文字解释**（`GameBootstrap.ts:493-499`）：只有 `playReject` + `playBoardReject`，
   缺 Web `2623-2624` 的两条 toast。噩梦模式下这是玩家理解「为什么拖不动」的唯一通道。
2. **`TAP_SLOP` 单位不同**：Cocos `GameBootstrap.ts:53` 是 14 **画布** px（设计 1080 宽），
   Web 是 14 **屏幕** px；实机分辨率 ≠1080 时「算不算点击」的阈值实际不同。
3. **`swapMisses` 计数从没被消费**：`doMove():494` 只自增（还写进断点），
   缺 Web `2626-2631` 的「连续 2 次无消除 → 自动提示」。
4. `onPointerCancel` vs Cocos 把 `TOUCH_CANCEL` 绑到 `onTouchEnd`（`:391`）：逻辑等价，可接受。

**补齐要动**：`玩法/GameBootstrap.ts` 的 `doMove()` 拒绝分支（加 toast）、`玩法/text.ts`（补规则提示文案）、
`GameBootstrap.ts:53`（TAP_SLOP 换算）、`doMove()`（补 `swapMisses>=2 → showHint()`）

## 5. 关卡目标类型

**Web 版**（`web/main.ts:2961-3028` + `核心/config.ts`）：

- **唯一目标是分数**：结束时 `score` 与 `star1/star2/star3` 比较，`settleLevel()` 判 0~3 星。
- **限时**：`timeLimitFor()` → 1~60 关 180 秒 / 61~120 关 240 秒 / 121~180 关 300 秒。
- **限步：不存在**（本作没有步数概念，只有时间）。
- **收集指定颜色 / 掉落物（坚果）/ 清除障碍：不存在**，没有这些目标类型。
- HUD 目标是「还差几分到下一档」（`updateGoal()` 2498）。

**Cocos 端**（`GameBootstrap.ts:661-709`）：

- 同一套 `settleLevel` / `commitSettlement`（core 共享），同样的 `LevelOutcome` 组装 ✓
- 时限：`beginLevel():315` `this.timeLeft = this.cfg.timeLimit` ✓（值来自 core `config.ts`）
- 结算吊牌三档星级：`showHonorDialog():722` 走 `honorForLevel`（core 共享）✓

**判定**：`完整`
**差距**：无
**补齐要动**：无
