## 0. 一句话结论

**萌宠拼拼乐在玩法、真皮肤、Cocos 微信移植上领先；糖果小镇真正值得拿的是四样：① 通用地图编辑器（终结手写坐标表）、② 云同步客户端全套（填补零后端接入的空白）、③ 好友排行开放数据域完整实现、④ 微信适配坑清单（两边合并后几乎全覆盖）。** 两边玩法不同（三消 vs 拼图消除），玩法代码互不相干。

## 2. 可抄用资产（按价值排序）

### A. 通用地图编辑器 ⭐ 最大价值——终结手写坐标表

**是什么**：`universal-map-editor/`，Vite+TS 的可视化关卡地图编辑器，有给美术用的单文件发布版 `release/地图编辑器.html`（Chrome/Edge 双击即用，免安装）和配套《地图编辑器-操作手册》（`docs/地图编辑器-操作手册.md`，按美术视角写的操作步骤）。服务器上还部署过在线版（地址见服务器备忘，不写进本文档）。

**能干什么**（对照你们的痛点）：

| 编辑器能力 | 对应你们现在的做法 |
|---|---|
| 导入**原图底图**（不压缩、原分辨率铺满） | 美术出的 1080×3840 世界底图直接铺进去 |
| 「插入关卡节点」预设，**关号自增**、放一个编一个 | 手写 `W1_1_10_坐标表.json` / `新坐标表_1536x8192.json`，改版全重算 |
| 组件库 + **切图导入**（大图自动去背景切成单个素材） | `节点浮层制作方法.md` 手工流程 |
| **遮罩层**：标出小人不能走的地方，路线自动绕行（core/walkPath 寻路） | 无（当前关宠物是静态贴在节点上） |
| 章节划分、章末过渡、**地图检查**（合法性校验）、预览通关路线 | 无 |
| 撤销/重做、图层、视差、导出 .map.json / 资源包 | 无 |

**为什么值得**：你们的坐标表已经换了三版格式，每版都是人工算 x/y 再抄进 markdown 表格和 JSON；节点和底图的对齐全靠肉眼。编辑器把这件事变成「在底图上看得见地摆」，导出即数据。你们 README 里 `generateLevelPositions()` 也预留了「可替换为外部坐标表」。

**怎么接（建议轻量方案）**：

1. 美术/策划用发布版 HTML 打开底图，摆关卡节点（关号自动递增），可顺手画遮罩。
2. 导出 `.map.json`。
3. 写一个 ~50 行的转换脚本：`.map.json` 里带「关号」字段的组件，取 `x+w/2, y+h/2` 像素中心，输出 `{level, x, y}` 列表——就是你们坐标表的格式，直接喂 `MapBootstrap`。
4. （可选进阶）遮罩数据 + 糖果小镇的 `play/walker.ts`（路线计算+行走动画+镜头跟随，1.2~3 秒按路程）可以做出「通关后宠物沿路走到下一关」——糖果小镇首页已有成品效果。

**不建议**：把糖果小镇整套 Canvas 渲染栈搬进 Cocos。编辑器当**出数工具**用，渲染留在你们自己的 Cocos 层，这是成本最低、收益最大的切法。

**注意**：.map.json 里底图是内嵌 data URL，文件会大（9MB 底图 → 文件约 +12MB）；它只是编辑器工程文件，转出来的坐标表才是游戏要的东西。糖果小镇的 `scripts/build-minigame.mjs` 里有现成的「从 map.json 抽大图成文件」的参考实现。

### B. 云同步客户端全套 ⭐ 填补最大架构空白

**现状**：你们全仓没有任何游戏后端客户端（无登录、无云存档、服务端排行、服务端体力）。上线前这一整块都要补。

**糖果小镇有现成的**（`universal-map-editor/src/minigame/cloud.ts`，217 行纯 TS）：

- 登录：`wx.login` code → `POST /game/api/auth/login` 换 JWT（+playerId），token 存本地；
- 云存档：`GET /game/api/progress` 拉云端，与本地**逐关取大合并**（星取大、分取大、解锁取大），合并结果既写本地也回推云端；
- 结算上报：`POST /game/api/level/result`，**失败进离线队列**（上限 200 条），下次启动补传；
- 401 统一处理（清 token 转纯本地）；资料推送（昵称/头像 PUT，后端校验违规词，失败回滚）。

设计原则一句话：**「本地是真相，网络尽力而为」——弱网/离线不卡玩法**。这正是小游戏环境（地铁、弱网、切后台）最需要的不变量。

**怎么接**：`cloud.ts` 不依赖 Canvas，只依赖 Host 接口的 4 个方法（`login / request / getStorage / setStorage`）。在你们 Cocos 工程里给这 4 个方法各写一个 wx 实现即可（你们的 `玩法/storage.ts` 已有存储封装，等于只剩 login + request 两件事）。接口契约表见首页交接文档 §五。

**⚠️ 关键前提（决策项）**：candy-game-server 目前是**单游戏配置**（AppID/密钥配一份，`WX_MINIAPP_APPID`）。两个游戏不能共用同一套部署——登录 code2session 会用错密钥，玩家数据会混。两条路：
1. **为萌宠拼拼乐单独部署一套 candy-game-server**（新小游戏 AppID + 新数据库）。服务器运维你们已经熟（mini-assets 静态目录就是你们配的）；后台管理（玩家管理、对局流水、防作弊审核、数据看板、Excel 导出）都是现成的，等于白拿一个运营后台。
2. 或后端加 game 维度改造（工作量大，不推荐首期做）。

### C. 好友排行（开放数据域）完整实现

微信硬性限制：主域读不到好友数据，只能在「开放数据域」子域里读并画到 sharedCanvas，主域把整张画布贴上屏幕。这块的坑（wxgame 协议 score 形状、KVDataList、postMessage 指令式通信）糖果小镇已全部踩平：

- 主域侧：`src/minigame/wxFeatures.ts` —— `wx.setUserCloudStorage` 写入 `{wxgame:{score, update_time}, totalStars, unlocked}`，sharedCanvas 尺寸管理、按需重画；
- 子域侧：`wx-template/open-data/index.js` —— **纯 ES5 独立脚本**（不走 TS 构建、不走引擎），读好友 KV、排序、画榜，整个目录原样拷进小游戏包即可。

对 Cocos 工程完全适用——开放数据域本来就在引擎之外。全服榜走 candy-game-server、好友榜走微信托管数据，两者互补，正好拼成你们排行榜页的两个子栏（你们现在只有本地数据）。

### D. 体力前后端双轨（`src/minigame/stamina.ts`，150 行纯逻辑 + 单测）

你们的体力目前是纯本地规则（上限 10 / 20 分钟）。接后端时的推荐模式（糖果小镇已验证）：

- **双轨**：已登录 → 以后端为准（进关 consume / 通关 refund，规则由服务器下发优先）；未登录/请求失败 → 本地按同一套规则兜底，弱网不卡玩家；
- **pending 计数**：本地模式记「已扣未结算」局数，返必须有对应扣除，防白嫖；
- **倒计时本地化**：服务器只给 `nextInSec`，客户端换算回本地时间戳后自己走，不用轮询；
- 纯函数核心（recover/consume/refund/nextInMs）+ vitest 单测，改规则先跑测试。

### E. 微信适配坑清单（两边合并版）

两边踩的坑**几乎不重叠**，合并后是一份相当全的 checklist。我们踩过的（你们 README 里没有）：

| 坑 | 说明 |
|---|---|
| 胶囊按钮让位必须保底 | `getMenuButtonBoundingClientRect()` 在开发者工具里可能拿不到，必须 `状态栏+40` 兜底再校正 |
| 小游戏 canvas 无 `style` | `cv.style.width = ...` 直接 TypeError 启动即崩 |
| 图片加载别依赖 `decode/naturalWidth/complete` | 微信里行为不一致，用自封装 ready 判断 + 加载完回调重画 |
| `wx.getStorageSync` 可能返回非字符串 | 存过对象时直接返回对象，读时统一归一化成字符串再 parse |
| 没有 DOM 输入框 | 昵称编辑用 `wx.showKeyboard` + `wx.onKeyboardConfirm`；确认框 `wx.showModal` |
| game.js 超 2000KB 工具不编译 | 我们用「构建时把地图大图抽成文件」解决；你们用远程包解决（你们的方案更彻底） |

你们踩过的（记录在案，双方共享）：sprite-frame meta 类型、场景压缩 UUID、Babel loose 展开对 Set/Map 的破坏、`getUILocation` 与 `screenToWorld` 的坐标换算、平台值 undefined 时 NaN 传染整块布局（数值校验+夹区间）、贴纸 PNG/JPG 去重、触摸分发途中切换节点导致输入失效。

## 3. 不建议抄的（避免白费工）

| 资产 | 原因 |
|---|---|
| 三消玩法全套（candy-trail.html、gen-candy.mjs、candy.generated.js） | 玩法不同。gen-candy 那套「HTML 内联脚本抽成模块防 eval」是纯 Canvas 单文件路线的专用解法，Cocos 用不上 |
| 纯 Canvas 外壳 UI（ui/shell、ui/draw、ui/theme） | 你们已有真皮肤的 Cocos 面板，比我们的 emoji 占位领先一个版本 |
| 排行榜产品形态 | 你们的（总分榜/关卡榜双 Tab、我的成绩条、领奖台、挑战本关）比我们的完整，该是反向输出 |
| 包体/发布方案 | 你们已跑通远程包 + 合法域名，比我们走得远 |
| 音频方案 | 你们离线合成 WAV 的方案对 Cocos 更对（我们是运行时合成） |

## 5. 建议的动手顺序

1. **先做后端决策**（单独部署一套 candy-game-server 实例 vs 改造加 game 维度）——它决定 B/C/D 三项什么时候能接。单独部署是推荐路线，运维成本你们已经具备。
2. **地图编辑器试点**（半天）：美术拿发布版 HTML 在一张现有世界底图上摆 12 个关卡节点，导出 .map.json，写转换脚本喂 MapBootstrap，验证链路顺不顺手。顺了再谈遮罩/行走小人。
3. **云同步客户端移植**（1~2 天含联调）：cloud.ts 四个 Host 方法适配到 Cocos，接 login/progress/level/result。
4. **好友排行**：open-data 目录直接拷，配 wxFeatures 的 KV 上报。
5. **体力接后端**：套双轨模式，规则参数换成你们的（10 上限/20 分钟）。
